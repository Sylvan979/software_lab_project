# 大模型辅助开发记录

本文档记录实验三中使用大模型（Anthropic Claude Code）的过程、生成内容、异常输出与处理方式，可直接作为实验报告“大模型辅助实现”一节的素材。

## 1. 总体协作方式

采用“需求 → 设计约束 → 存根与规约 → 实现 → 验证”的分解方式，而不是一次性让模型生成整个项目：

1. **提供固定上下文**：每轮任务都附带分层约定（`ui → services → repository → domain`）、实验二的类图/状态图要点、REQ 编号、命名与持久化约定。
2. **按层拆分**：领域模型 → 数据访问 → 业务服务 → 定时任务 → 界面，每层先写代码与测试，通过后再进入下一层。
3. **先接口后实现**：先确定服务方法签名、异常类型和返回结构，再让模型填充实现，减少接口漂移。
4. **生成即验证**：每批代码生成后立即执行 `python -m compileall`、`python -m unittest`、`python -m app.cli demo`；界面代码额外做四端冒烟测试。
5. **人工审查**：逐行阅读生成结果，重点检查状态迁移、金额计算、权限校验和异常分支；发现的修改单独提交并注明 `[人工修改]`。
6. **Git 分支持续集成**：每层在独立特性分支完成，测试通过后 `--no-ff` 合入 `main`，保持可回溯的工程记录。

## 2. 大模型承担的工作

| 阶段 | 生成内容 |
| --- | --- |
| 领域层 | 实体数据类、角色继承、枚举与中文标签、订单状态机迁移表、计价函数 |
| 数据访问层 | 原子写入的 JSON 数据库、通用仓储、类型编解码器、13 类专用仓储 |
| 业务服务层 | 登录/锁定、店铺与菜单、购物车、结算与幂等、支付、配送、退款仲裁、统计、通知、审计 |
| 定时任务 | 支付超时、接单超时、退款自动同意、派单升级、24 小时自动收货 |
| 界面层 | 登录/注册、顾客/商家/骑手/管理员四端视图、主题与通用组件、模态对话框 |
| 测试 | 34 项单元/集成测试及测试数据构造 |
| 工程化 | pylint 清理建议、README 与设计映射文档初稿 |

所有代码由大模型生成后经人工阅读、运行与测试确认；提交信息用 `[AI 生成]` 标识生成提交，修复与调整用 `[人工修改]` 标识。

## 3. 不符合预期的输出与处理

| # | 现象 | 发现方式 | 原因 | 处理与预防 |
| --- | --- | --- | --- | --- |
| 1 | 订单仓储用 `store_id` 当主键，更新订单时覆盖同店其他订单 | 仓储往返测试 | 通用仓储按固定属性优先级取主键，`store_id` 排在 `order_id` 前 | 改为按 dataclass 字段声明顺序取第一个非空 `*_id`；增加嵌套订单持久化测试 |
| 2 | `autosave=False` 时显式 `save()` 不落盘 | 命令行演示数据丢失 | 保存逻辑把“是否自动保存”误用到显式保存 | 显式 `save()` 始终写盘，只有 `mark_dirty` 遵守 autosave |
| 3 | 演示数据初始化抛“管理员不能自助注册” | 首次运行即失败 | 种子数据复用了面向用户的注册接口 | 管理员改为系统直接插入，符合 REQ-001 的预置账号规则 |
| 4 | 命令行演示下单失败：金额低于起送价 | `python -m app.cli demo` | 演示商品数量不足 | 调整演示数量，并在演示脚本中打印校验信息 |
| 5 | 命令行打印的订单状态是旧值 | 人工核对输出 | 服务返回新对象，脚本仍引用迁移前的对象 | 统一使用返回值/重新查询后的对象 |
| 6 | 重新派单后确认取餐抛 `配送中 → 配送中` 非法迁移 | 配送异常测试 | 重派订单已处于“配送中”，取餐逻辑仍无条件迁移 | 取餐时仅在“待配送”状态触发迁移；补充“异常→重派→取餐→送达”测试 |
| 7 | 骑手视图对手机号调用地址脱敏函数，输出异常 | 代码审查 | 混用了 `mask_detail` 与 `mask_phone` | 按字段选择脱敏函数；界面冒烟测试覆盖骑手详情 |
| 8 | 多处未使用导入、超长行、`type(None)` 写法 | `pylint app` | 分批生成造成的冗余 | 清理导入与行宽，改用 `types.NoneType`；将消息列表抽为共用 `MessagePanel`，pylint 10.00/10 |
| 9 | 命令行演示第二次运行时报“已完成订单不能支付” | 重复执行 `python -m app.cli demo` | 演示脚本使用固定幂等键，复用了上次运行留下的已完成订单 | 幂等键加入时间戳，演示可重复执行；同时保留同一次运行内两次提交的幂等断言 |

处理原则：**不直接接受模型的“看起来合理”**。每个异常都先写一个能复现的测试或命令，再修改实现，最后重跑全部测试，避免修一处坏一处。

## 4. 提高生成质量的提示词要点

- 明确“只改哪些文件、不要改哪些层”，避免模型跨层重写。
- 给出业务规则的具体数值（支付 15 分钟、接单 5–20 分钟、退款 10 分钟、3 km、起步价 5 元 + 1 元/km），而不是“合理设置超时”。
- 要求“异常必须使用项目已有异常类型”“所有状态迁移必须经过 `OrderLifecycle`”，减少自造 API。
- 要求同时生成测试，并说明测试应覆盖的失败分支（重复结算、越权、库存回滚、超时）。
- 对界面任务提供控件结构与交互约定（标签页、按钮、只读详情），并要求所有操作经 `BaseView.guard` 兜底。
